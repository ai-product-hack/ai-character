# S1 — стенд сквозной задержки

    ../../bench/r1-stt/.venv/bin/python pipeline.py --both

Проходит весь путь mic→STT→эндпоинтер→LLM→TTS→висемы→«динамик» на клипах из
`data/audio/`, с отметкой времени на каждой границе, и печатает раскладку
бюджета от **конца речи пользователя**.

Провайдеры меняются в `config.json`. LLM по умолчанию `mock` с настраиваемым
`ttft_ms` — спекулятивная генерация это свойство механики, а не провайдера,
и её выигрыш меряется без ключей. Реальный провайдер добавляется классом с
методами `prefill_only()` и `generate()` в `build_llm()`.

`--both` прогоняет со спекуляцией и без неё, чтобы выигрыш был виден числом.
Сырьё: `../../bench/results/s1_latency.jsonl`.

## Измерено 2026-09-03, mock LLM (TTFT 600 мс), 25 клипов × 2 режима

Итог считается **от конца речи пользователя** до момента, когда первый кусок
аудио готов к воспроизведению. Прогоны, где детектор дал ложный срез
(сработал раньше конца речи), исключены из агрегата — это другой исход,
и усреднять его с нормальными нельзя.

| режим | итог p50 | итог макс | prefill успел |
|---|---|---|---|
| спекуляция ВКЛ | **2095 мс** | 2332 мс | 19/20 |
| спекуляция выкл | 2362 мс | 2603 мс | 0/20 |

**Выигрыш спекуляции: ~267 мс медианы.** Важнее самой цифры то, что
**prefill успевает завершиться до срабатывания эндпоинтера в 19 случаях из
20** — то есть механика по времени проходит, а не только по идее.

Оговорка про магнитуду: у mock-провайдера экономия ограничена сверху
настроенным `prefill_ms`, поэтому 267 мс — это свойство конфигурации, а не
измерение выигрыша. **Измерением является доля успевших prefill (19/20) и
сквозной итог.** Реальную величину экономии даёт прогон с настоящим
провайдером: `--provider deepseek`.

### Замечание о разрешении эндпоинтера

Первая версия стенда давала эндпоинт на 1730–1900 мс вместо 1450 мс из R2.
Причина оказалась в стенде: детектор получал кадры пачкой после каждого
STT-чанка, и решение квантовалось по 480 мс. После перевода цикла на кадры
512 отсчётов (32 мс) с подачей в STT каждые N кадров эндпоинт встал на
1460–1550 мс, совпав с R2.

**Практический вывод для реализации: эндпоинтер надо тактировать мелкими
кадрами независимо от размера чанка STT.** Иначе пол-чанка теряется на ровном
месте.

### Почему один запуск prefill не работает

Первая версия запускала спекулятивный запрос один раз, как только транскрипт
достигал 12 символов. Результат — **0 попаданий из 20**. Причина в данных:
к моменту срабатывания эндпоинтера ранний промпт покрывал лишь **треть**
финальной фразы (медиана покрытия **0.35**), а отвечать на треть вопроса
нельзя — запрос приходится выбрасывать.

Рабочая версия перезапускает запрос при росте транскрипта на 40%, держа в
полёте самый свежий вариант. Покрытие вырастает до **0.98**, попадания —
12 из 20, медиана 2 перезапуска на реплику. Цена: 2–3 запроса к API вместо
одного, из которых оплачиваются все.

**Это не деталь реализации, а условие работоспособности приёма.**
Спекулятивная генерация «в один выстрел» на живой речи не окупается вообще.

## Бэкчэннел (измерено 2026-09-03)

Включается в `config.json`: `"backchannel": {"enabled": true}`.
Фразы синтезируются **один раз при старте** и хранятся готовым PCM — в момент
срабатывания эндпоинтера нельзя тратить даже 9 мс на Silero.

Измерено: бэкчэннел уходит через **131 мс** после решения эндпоинтера
(макс 163 мс, 5 прогонов).

| | n | первый звук, медиана | **в пороге 3000 мс** |
|---|---|---|---|
| быстрый путь эндпоинтера | 13 | 517 мс | **13 / 13** |
| безопасный путь | 40 | 1809 мс | **40 / 40** |
| без бэкчэннела | 53 | 3649 мс | 21 / 53 |

Не ускоряет ответ — только первый звук.
