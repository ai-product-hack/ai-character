# S3 — отмена по generation_id

    python3 server.py     # http://localhost:8070

Сервер отдаёт аудио кадрами по 20 мс, помеченными `generation_id`, и специально
бежит впереди реального времени (3× по умолчанию) — как настоящий TTS.
Клиент безусловно дропает кадры с чужим `gen`, даже если сервер не успел
остановиться. Три режима перебивания сравниваются в таблице; сырьё пишется в
`../../bench/results/s3_cancel_server.jsonl`.

## Измерено 2026-09-03 (Chrome, macOS 26.6.2, M4, 44.1 кГц)

Сервер отдавал поток на 3× быстрее реального времени; к моменту отмены у
клиента было накоплено ~6.9 с аудио.

| режим перебивания | остановка | + выход устройства | итого | порог 300 мс |
|---|---|---|---|---|
| только перестать кормить | **6960 мс** | 24 мс | 6984 мс | **мимо в 23 раза** |
| flush без fade | 0 мс | 24 мс | **24 мс** | проходит |
| flush + fade 25 мс | 23 мс | 24 мс | **47 мс** | проходит |

Серверная часть отмены не является узким местом вообще: от получения
`/cancel` до прекращения отправки проходит **0.1–7.2 мс**.

**Вся задержка сидит в клиентском аудиобуфере.** Подозрение из постановки
задачи подтвердилось буквально: отмена на сервере и прекращение подачи в
плеер не останавливают звук, потому что уже накопленное продолжает играть.
Останавливать надо **выход**, а не подачу.

Fade на 25 мс стоит 23 мс сверх жёсткого стопа — при пороге 300 мс это
бесплатно, и его надо ставить. Оговорка: я измерил тайминги, но **не мог
послушать**, щёлкает ли жёсткий стоп; разрыв волны на произвольной амплитуде
щелчок даёт по построению, а цена страховки — 23 мс.
